# 曜核、映序与棱光：协作边界

本说明区分现有协议、可选适配链路与实际验收。曜核从 2.9 起提供跨工具项目/报告索引、能力声明与任务队列；2.10 增加内置模板、发现候选和手动登记的工作端接入中心。现有整合包含 [aihub-execution/1 可选执行协议](EXECUTION_PROTOCOL.md)：冻结请求与声明、持久幂等回查、精确发布客户端领取、原生观察、取消意图以及分类报告。映序与棱光已有显式接入的可选链路候选；目录或登记本身仍不创建适配器，也不自动启动执行。

2026-09-25 用户进一步明确：**三款软件必须各自独立使用，协作是可选能力。** 映序和棱光可以直接连接或通过文件交接，曜核不是必经服务。未安装、关闭或断开任意一款时，其他应用原有本地功能照常可用；不要求共同账号、共享数据库或迁移到统一目录。棱光生成仍需其已配置的 ComfyUI/模型环境。

## 各自负责什么

| 产品 | 主要职责与数据主责 | 配合方式 |
| --- | --- | --- |
| 曜核 | 工作区规范、公共模型/LoRA/工作流索引、跨工具任务与报告、经审核共享记忆、能力目录 | 关联项目和已有文件；按任务分配工作目录；记录来源与执行状态 |
| 映序 YingXu | 创作项目、笔记、角色/场景/镜头、素材关系、制作进度、版本和交付文件；项目 Skill 绑定 | 维护创作项目的主记录，通过 API 提供上下文和接收资产 |
| 棱光 PrismCanvas | 生成画布、ComfyUI 工作流和参数、图像/视频任务、任务结果与重现配方 | 接收生成任务，返回任务 ID、结果及配方供项目收录 |
| 已登记工作端，包括 Codex / ZCode / WorkBuddy / DSH 模板及自定义工具 | 由实际接入客户端按已配置能力执行任务 | 普通队列需客户端主动领取、使用分配目录、登记报告/结果；可选执行需另行授权并由精确发布端领取。手动模式仅接收项目说明 |

模型和 LoRA 仍属于曜核的公共资源域：一个底模可用于多个映序项目和多个棱光任务。按资源类型、兼容架构、用途与实际引用管理；不要为每个项目复制一套模型。数据集、训练运行、验证图和选版报告保留各自的目录角色，训练 captions 不进入报告库。

曜核的“项目”页是跨工具索引，不再承担第二套笔记编辑、分镜编辑或素材生产界面。映序的成片管理指对交付文件的组织，不等于已具备视频剪辑渲染。Skill 索引也不等于执行器：发现 Skill 文档只表示存在声明，适用性、依赖、客户端连接和实际调用要分别记录。

## 本机代码/交付文档已核实的接口基础

2026-09-25 核对映序本机 0.4.20 代码及 API_CONTRACT.md、功能指南，棱光 0.5.0 交付包 README 和 docs/AI_INTERFACE.md。以下两段描述这一历史接口基线；后续可选协作候选与验收范围见下节，不能由这些旧版本说明推断当前安装状态。

映序提供项目、项目条目、Skill 目录和项目上下文读取；上下文导出包含 PROJECT_CONTEXT、progress 与 files-index。资产导入使用 `/api/import` 的显式 `copy` 或 `reference` 模式，并跟踪导入任务。写入经应用自己的鉴权和 API 完成，禁止直接改映序数据库。Skill 可用于上下文与项目绑定，映序自身不自动执行 Skill。

棱光的 0.5.0 基线提供本机 MCP Streamable HTTP 接口，包括 `fw_status`、`fw_environment`、`fw_diagnostics`、`fw_packages`、`fw_package_inspect`、`fw_package_import`、`fw_package_export`、`fw_compile`、`fw_upload_image`、`fw_generate`、`fw_jobs`、`fw_job_recipe`、`fw_retry`、`fw_cancel`。每次启动的端口和令牌需要从其连接信息获取，不能硬编码端口。生成使用稳定 `request_id`；响应不确定时应保留原 ID 并核对既有任务，不能盲目重发并重复生成。该历史基线没有证明专用的按 `request_id` 精确重查接口；后续执行适配的账本与 outbox 恢复应按对应协议和候选证据判断。

曜核 2.9.0 新增能力声明、列举、匹配和派单 MCP 工具。当前派单写入已有协作队列，接入的 harness 需主动领取并执行；没有后台执行端时任务保持待领取。评分仅为元数据匹配，不代表效果、速度或成本实测。

2.10 的[工作端注册表](HARNESSES_2.10.md)允许登记其他执行工具；提供方、MCP 服务名、工作端类型与客户端实例仍分别管理。登记一个名为映序或棱光的条目不会自动创建应用适配器，也不会使其具备队列领取或资产回写能力。成功调用曜核协议与完成原产品业务链路是不同的验收层级。

## 已有可选链路与验收范围

2026-10-02 的既有 2.13.10 协作闭环验收记录覆盖三个真实产品 HTTP 进程、实际 Worker/NativeApp 和自有 MockComfy 生成提供方：冻结请求只形成一项执行和队列任务，结果身份/manifest/字节/摘要一致，映序原轮次显式收件并待用户审核；固定包另有真实 TCP 进程重启、丢回复恢复与并发/事务证据。该记录中曜核 2.13.10 的正式本地安装及公开发布已完成，映序 Stage I 与棱光 Phase7N 为隔离候选验收，未替换两款软件的正式安装。

本轮整体可用性候选是后续独立工作目录；上述历史包和安装记录不替代本轮源码、构建、界面、固定包或正式替换验收。本轮普通派单的回复丢失与硬刷新恢复见 [能力目录与任务调度](CAPABILITIES_2.9.md)。用户仍可独立使用任意一款，或选择文件交接、两应用直连、曜核可选调度；协作须显式配置与授权，不能由安装、工作端心跳或能力声明自动开启。

历史取消 case 已发送真实原生取消请求，任务随后自然完成并保留产物；没有证明真实生成引擎中断成功。取消意图、原生终态和报告完成分别记录。既有验收也不证明所有模型、平台或未接入 harness 自动执行、自动收集报告；共享记忆候选仍需用户审核，公共 source-read/read_result 扩展尚未实现。

映序的编辑器、项目管理和 Skill 绑定保持独立。下面是三款同时参与时的可选流程，具体合作端须实现其对应步骤：

1. 从映序选择已有项目，以 `owner_app + external_project_id` 关联主项目；曜核只保留关联、路径和同步状态，不创建另一个同名创作项目。
2. 读取明确授权的映序项目上下文。任务只传所需资产引用、目标、约束和输出要求；令牌单独保存在用户控制的本机设置，不能出现在能力目录、任务描述和报告中。
3. 曜核按已连接执行端和能力限制提出方案。生成任务经棱光适配器进行环境检查、编译、提交、查询；任务状态包含等待、执行、成功、失败及结果不确定，支持取消和幂等重查。
4. 将生成结果路径、配方、模型/LoRA 引用、执行端及时间作为来源记录；经映序 API 导入或引用到原项目，等待导入完成后再登记协作任务交付。
5. 正式报告归任务 Reports；生成文件归任务 Outputs 或主应用约定的资产位置；临时文件才可按规则到期回收。跨工具长期记忆须有来源并经审核，原生会话/内部记忆不整库抓取。

每个新适配或新候选仍须分别核对独立使用、“映序选项目 → 棱光生成 → 映序收录”和三方可选调度，并验证失败/重试不重复生成、不重复导入。执行完成与交付/收录完成分别记录；待收录产物保持可恢复，不能作为普通到期临时文件清理。仅有接口文档、心跳或队列成功都不能替代该验收。

同一套项目引用、任务请求、产物清单与接收回执可经文件、HTTP 或 MCP 适配传递。标识来自对象所属应用，不以曜核目录中的 ID、项目名或某台电脑的盘符作为全局身份。凭据与本机连接配置不进入交接清单。实现不得将说明性文字或能力发现当作执行授权。

## UI 原则

首页保留模型管理、素材管理入口；工作报告与能力中心各有入口。侧栏按资源管理、项目与协作、工作区与维护组织，图片生成记录作为素材管理的内部专题，图片/视频/音频按媒体类型浏览；具体索引范围见 [资源导航职责](RESOURCE_NAVIGATION.md)。项目页显示归属应用、关联和索引范围，创作编辑通过原应用完成。清楚区分已登记产物、只读索引和历史资料；缺失、部分扫描、未连接、待领取均明确显示。无需将三款软件强制改成同一种视觉风格。
